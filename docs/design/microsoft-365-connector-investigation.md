# Microsoft 365 connector investigation

## Summary

Investigate the unified Work IQ remote MCP server first. It covers the requested Microsoft 365 workloads and is the closest fit to Switch's remote OAuth connector shape. Keep the Microsoft 365 placeholder disabled until a tenant test proves the callback, consent, identity and renewal paths. Test the documented `WorkIQ.Read` scope first. The live MCP metadata advertises the write-capable `WorkIQAgent.Ask` scope, so a read-only level depends on proving the endpoint accepts and enforces `WorkIQ.Read`. Microsoft Graph offers that scope boundary and a straightforward profile lookup, but its official directory MCP preview covers a different workload and Microsoft retired the Graph CLI. A Graph implementation for these workloads would need a separately approved transport. [Work IQ API overview][iq-api] · [Work IQ permissions][iq-perms] · [Microsoft MCP Server for Enterprise][enterprise] · [Graph CLI retirement][cli-retire]

## Work IQ

| Area | Evidence |
| --- | --- |
| Status | **Documented.** Microsoft announced Work IQ API general availability on June 16, 2026. The unified MCP overview still marks `retrieve` as public preview. The Agent 365 documentation separately labels its workload-specific MCP servers as preview. These are different surfaces. [GA announcement][ga] · [Unified MCP overview][iq-mcp] · [Agent 365 preview][agent365] |
| Endpoint and tools | **Documented.** The unified endpoint is `https://workiq.svc.cloud.microsoft/mcp`. Generic `fetch` and `fetch_blob` read entities and files. `search_paths` and `get_schema` discover paths and schemas. `create_entity`, `update_entity`, `delete_entity`, `do_action` and `call_function` cover changes, actions and functions. `ask` and `retrieve` provide reasoning and grounding. Microsoft describes Outlook mail, calendar, OneDrive and SharePoint files, and Teams messages. Examples include `/me/messages`, `/me/events`, `/me/drive/items/{item-id}/content` and `/me/chats/{id}/messages`. [MCP overview][iq-mcp] · [Tool reference][iq-tools] · [API overview][iq-api] |
| Registration and consent | **Documented.** Work IQ uses delegated Entra OAuth. Microsoft documents customer-owned Entra app registration and administrator consent for `api://workiq.svc.cloud.microsoft/WorkIQAgent.Ask`. Public resource metadata advertises the same permission with the resource application's GUID as the prefix and names the `organizations/v2.0` authority. The permissions reference also lists admin-consented `WorkIQ.Read` and `WorkIQ.Act`, but neither appears in the endpoint's public scope list. The endpoint metadata and the API-wide permissions table answer different questions. The authority's public metadata advertises neither a dynamic registration endpoint nor a token revocation endpoint. Use static registration as the working design. [Permissions][iq-perms] · [App setup example][iq-foundry] · [Resource metadata][iq-metadata] · [Entra discovery][entra-metadata] |
| Redirect and PKCE | **Documented.** Entra supports S256 for authorization-code flow. It permits HTTP localhost callbacks and ignores the port for registered localhost callbacks. An HTTP literal `127.0.0.1` callback is registered through the app manifest. Microsoft demonstrates a public desktop callback for the separate Agent 365 workload servers. That example establishes support for that product and client type. [Authorization-code flow][code] · [Redirect rules][redirect] · [Agent 365 public-client example][agent365] |
| Token lifetime and refresh | **Documented.** Entra normally issues access tokens with 60–90 minutes of lifetime, with exceptions for policies and clients such as those using Continuous Access Evaluation. The v2 authorization flow needs `offline_access` for refresh. For ordinary non-SPA cases the documented refresh-token default is 90 days. Entra returns a replacement refresh token but does not spend the old one on use. Store the replacement and discard the old copy. This corresponds to Switch's `refresh: reusable` semantics. [Access tokens][access-token] · [Authorization-code flow][code] · [Refresh tokens][refresh] |
| Regions | **Documented.** Microsoft publishes region exclusions for its hosted Work IQ connectors, including US government and China clouds, with the exact exclusions depending on the host product. It also notes regional rollout of administrative tooling. These tables describe those products. Start any Switch trial with a commercial tenant on the documented endpoint. [Hosted connector regions][regions] · [Regional tooling note][agent365] |
| Limits and errors | **Documented.** The tool reference gives a default 4 MB raw-file limit for `fetch_blob`, a cap of 10 chat messages per request, and tenant limits on collections. It describes downstream status, `Retry-After` on throttling and request correlation IDs. Clients own retries. A result cap is separate from a request-rate quota. The unified MCP documentation reviewed here does not publish a numeric request-rate quota for this endpoint. [Tool reference][iq-tools] |
| Tenant checks | **Not verified.** W1–W6 and W8 below cover endpoint access, redirects, workloads, token behavior, regions, throttling, billing and effective policy. W7 covers account identity. |

Microsoft published Windows, Linux and macOS archives for `msgraph-cli` 1.9.0. Switch could compute SHA-256 over each exact official archive and pin the URL, digest and extracted binary path. The asset listing supplies no SHA-256 digest for those archives. A pin would verify the chosen bytes, while maintenance and security servicing would still depend on the vendor. Microsoft archived the repository in August 2025 and scheduled full retirement for August 28, 2026. Exclude it from a new connector. [Official release assets][cli-assets] · [Official installation instructions][cli-repo] · [Retirement notice][cli-retire]

Microsoft recommends the maintained Graph PowerShell SDK. It accepts a caller-supplied bearer token via `Connect-MgGraph -AccessToken` and provides `Invoke-MgGraphRequest` for Graph REST calls. That is a PowerShell module and cmdlet interface. Pinning a PowerShell release or module archive alone would still leave Switch needing a reviewed host-only wrapper with fixed operations, controlled module loading, and no agent-supplied script, command string or arbitrary URL. Microsoft's documented Agent 365 route for arbitrary Graph scenarios is to build a scenario-specific server. It does not supply a ready-made connector for these four workloads. Work IQ's own npm CLI is another Work IQ client and inherits that service's consent and billing model. ### Delegated Graph permissions for an initial read level

The consent column is Microsoft's permission-definition flag. Tenant consent policies can still require an administrator for a scope whose flag is No. Microsoft's current recommended policy, for example, restricts user consent for `Mail.Read`, `Calendars.Read`, `Sites.Read.All` and `Chat.Read`. Choose operations first and test each with the smallest scope set. [Permissions reference][graph-perms] · [Entra consent policy][consent]

| Operation | Candidate delegated scope | Admin consent flag |
| --- | --- | --- |
| Read Outlook mailbox content | `Mail.Read`. Use `Mail.ReadBasic` for metadata-only use. [List messages][mail] · [Mail permissions][graph-perms] | No for both |
| Read calendar event details | `Calendars.Read`. Use `Calendars.ReadBasic` if the limited event fields suffice. [List events][calendar] · [Calendar permissions][graph-perms] | No for both |
| Read the user's OneDrive files | `Files.Read` for the user's files and known drive items where the endpoint permits it. Add `Files.Read.All` only if access to all files the user can reach is essential. [List drive children][drive] · [File permissions][graph-perms] | No for both |
| Resolve SharePoint sites and read documents | `Sites.Read.All` for general site lookup, covering the sites the signed-in user can access. For a fixed site, evaluate delegated `Sites.Selected` with a separately provisioned read assignment and verify the exact operations. [Get site][site] · [Selected permissions][selected] · [Site permissions][graph-perms] | No for `Sites.Read.All`, Yes for `Sites.Selected` |
| Read Teams chat messages | `Chat.Read` for the user's one-to-one and group chats. [List chat messages][chat] · [Chat permissions][graph-perms] | No |
| Read Teams channel messages | `ChannelMessage.Read.All` for channels the user can read. The resource-specific `ChannelMessage.Read.Group` in the endpoint table is application permission and belongs to a different authorization model. [List channel messages][channel] · [Channel permissions][graph-perms] | Yes |
| Identify the signed-in user | `User.Read` for Graph `GET /me`. [Graph profile][me] · [User permissions][graph-perms] | No |

## Licensing and Copilot Credits

**Documented.** Work IQ API has no separate per-user Work IQ license. For a third-party client, Microsoft documents usage-based Copilot Credits even for users with a Microsoft 365 Copilot license. Built-in Microsoft 365 Copilot experiences and the separately documented Agent 365 workload preview have different licensing rules. The Work IQ enablement guide requires a usage-based billing plan associated with an Azure subscription and resource group, with the test user assigned to it. The tenant administrator can govern access and spend in the Microsoft 365 admin center. Sandbox eligibility and workload sample data establish a Graph test environment. Work IQ usage and billing eligibility for the proposed sandbox still need a check. [Developer sandbox setup][sandbox]

## Write policy

**Documented.** The unified MCP server evaluates each request against the resource path, operation, request contents and tenant/user context. Default policy blocks mutations, including actions such as sending mail. A tenant administrator authorized to manage Work IQ or Copilot settings can change supported settings in **Microsoft 365 admin center → Agents → Tools → Work IQ MCP → Policy**. Changes can take up to 24 hours. The policy applies across the tenant. Underlying user permissions still apply. Surface a policy denial as a governance decision and reserve bounded retries for transient throttling. [Policy governance][policy] · [Tool errors][iq-tools]

Switch's November 3 ruling makes `tools: { mode: pass_through }` mandatory for OAuth. A skill can prefer bounded reads and require a person's explicit authorization for mutations, but the enforceable boundaries are vendor scopes and tenant policy. Offer a Work IQ read level only after a tenant test proves that `WorkIQ.Read` can perform the required reads and that mutation requests fail even under a write-permitting tenant policy. If the endpoint only works with a write-capable scope, the intended product shape is one plainly labelled write level. The current `ConnectionAccess` requires `read` and makes `write` optional, so a true write-only choice depends on the separate shared loader and connect-screen change that the maintainer approved on #834. Do not put a write-capable scope in the required `read` field. Graph can start with only the listed read scopes. Key-based catalog entries cannot be connected or granted under the current broker rules. [Switch connector rules](service-connections-v2.md#adding-a-connector) · [Switch keys](service-connections-v2.md#keys) · [Maintainer correction](https://github.com/sandbox-quantum/switch/issues/834) · [Work IQ scope][iq-perms] · [Graph permission model][graph-model]

**Not verified.** W8 covers a real denial, effective policy propagation, and authorized mutations on synthetic data.

## Identity mechanism

Switch's `ConnectionIdentity` accepts one HTTPS `url` and two dotted JSON paths, `account_id` and `label`. Core performs a bearer-authenticated GET using the same access token it just obtained. The loader cannot concatenate fields or accept a JWT claim as a path. The label is display text and the adapter falls back to the account ID when it is absent. [Loader](../../core/switch_core/connections/loader.py) · [OAuth adapter](../../core/switch_core/connections/adapters/oauth.py)

| Option | Field mapping and fit |
| --- | --- |
| Graph token and Graph profile | Set `url` to `https://graph.microsoft.com/v1.0/me`, `account_id` to `id` and `label` to `userPrincipalName` or `displayName`. `User.Read` and a delegated Graph token suffice. Graph `id` is the Entra object ID. Using `id` directly fits the current schema and requires no ID token. [Graph profile][me] · [Entra ID-token claims][claims] |
| Work IQ token and native profile | Look first for a supported, HTTPS JSON identity GET that accepts the Work IQ audience and returns a stable tenant-account identifier plus a display field. Work IQ `fetch` uses an MCP call and cannot stand in for the loader's HTTPS GET. Graph `/me` and Graph UserInfo require Graph audience tokens. UserInfo also provides a pairwise subject and display claims instead of an explicit tenant/object pair. A separate Graph token obtained with appropriate consent could look up the profile, but Switch would need a reviewed second-resource exchange and tenant binding. [Work IQ tool reference][iq-tools] · [Access-token ownership][access-token] · [UserInfo][userinfo] · [Authorization-code flow][code] |
| Validated Entra ID token | If a Work IQ-native identity endpoint is unavailable, propose a separately reviewed broker identity mode. Request `openid profile` alongside Work IQ scopes and validate signature against trusted issuer keys, issuer/tenant, app audience, nonce and timestamps before deriving `account_id = tid + ":" + oid`. Use a name or username only as `label`. Keep the ID token inside Core and use the Work IQ access token for tool calls. This is a design option outside the current `ConnectionIdentity` schema. [ID tokens][id-token] · [Claim validation][validate] · [ID-token claims][claims] |

Treat each resource tenant as a separate account, including a person's guest identity in a second tenant. Microsoft documents a different object ID per tenant even for the same sign-in credentials. Graph-only v1 can use the distinct Graph `id` returned in the authorized tenant. An explicit `tid:oid` key is preferable when a trusted tenant value is available, but the current loader has no composite field. Reconnecting to another tenant must require fresh grants for its distinct account. Never use email, UPN or unvalidated access-token contents as the account key. [Entra ID-token claims][claims] · [Access-token ownership][access-token] · [Switch grants](service-connections-v2.md#grants)

**Not verified.** W7 covers identity endpoint availability, claims and cross-tenant behavior with real users.

## What would change in Switch

- **Work IQ remote.** If a native identity GET exists and the confidential client works, the existing loader can support a static OAuth entry with one MCP server, `tools: { mode: pass_through }`, `refresh: reusable`, measured `token.max_lifetime` and a credential-free skill. A read-only entry additionally needs the vendor-enforced scope boundary described above. Use explicit HTTPS Entra endpoints as the first experiment. The discovery path requires advertised S256 and the inspected Entra metadata omits that field despite documented S256 support. Try the existing `core` HTTPS callback with an operator-owned confidential Web app first. Switch's static settings require a secret, so a public-client loopback-only deployment would need a separate approved settings change. The exact Console loopback path is `/switch-services/callback` on `127.0.0.1`. No callback host or PKCE exception is needed for the Web-app experiment. [OAuth adapter](../../core/switch_core/connections/adapters/oauth.py) · [Static client settings](../../core/switch_core/connections/registry.py) · [Callback paths](../../core/switch_core/connections/oauth_clients.py) · [Entra discovery][entra-metadata] · [Redirect rules][redirect] · [PKCE][code]
- **Lifetime and disconnect.** Measure the token lifetime before selecting a finite catalog cap. In particular, a cap copied from a one-hour vendor can hold back fresh Entra tokens with longer lifetimes. Use the current `remove_access` path if the vendor lacks a documented per-app token revocation endpoint. User-granted consent can be removed in My Apps where applicable. Tenant-wide consent requires administrator action in Entra. Do not substitute user-wide session revocation for an app disconnect. [Switch tokens](service-connections-v2.md#tokens) · [OAuth loader](../../core/switch_core/connections/loader.py) · [Entra discovery][entra-metadata] · [Remove user consent][user-consent] · [Review administrator consent][admin-consent]
- **Graph.** The existing identity lookup fits a Graph token, but direct REST needs a separately designed session-host transport or a supported, pinned vendor CLI that accepts broker-managed credentials without arbitrary shell execution. An approved transport would start with a read-only catalog level and a skill describing only supported operations. For a host wrapper, pin and verify the runtime and dependencies, allow only reviewed Graph paths and methods, and deny auth, config and administration commands at the agent boundary. The directory MCP preview and retired CLI are poor substitutes for that transport. [Graph profile][me] · [Enterprise scope][enterprise] · [CLI retirement][cli-retire] · [Switch connector shapes](service-connections-v2.md#adding-a-connector)
- **Approval boundary.** This report leaves the existing placeholder disabled. An ID-token identity mode, any tenant configuration field, public-client settings changes, a write-only catalog/UI shape and any new Graph transport wait for maintainer review. Before enabling an agreed route, add loader assertions for the shipped entry, and a skill covering bounded reads, explicit authorization before writes, policy denials and throttling. Keep all credentials inside the broker/session-host boundary and keep tenant data out of fixtures. [Switch connector rules](service-connections-v2.md#adding-a-connector)
